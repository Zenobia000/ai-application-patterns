# Capstone｜一家店的 AI 開幕週

> **一句話任務**：找一家真實的小店（或虛構一家「學生合作社咖啡店」），用這個工作坊學到的 Pattern，幫它準備開幕週需要的一切：網站、宣傳短影音、AI 店員、每週自動報表。**重點不是每一項都做到最好，而是說明你為什麼這樣組合。**

| 應用類別 | Pattern | 難度 | 預估時間 |
|---|---|:---:|---|
| B + C + D + F（+ A / E / G） | P1–P6 自由組合 | ★★★★ | 2–4 週（小組） |

---

## 1. 為什麼做這件事

前面每個 Lab 都是「一個問題 × 一兩個 Pattern」。真實世界不會這樣分好給你。

一家店開幕需要的東西，剛好橫跨所有應用類別：

| 開幕需求 | 應用類別 | 可能的 Pattern | 對應 Lab |
|---|---|---|---|
| 店家網站與菜單 | D 軟體 | P3 | Lab 04 |
| IG / 短影音宣傳 | C 生成媒體 | P1 + P4 | Lab 03 |
| 回答客人問題、接受預訂 | B 對話 | P2 + P4 | Lab 02 |
| 店內 3D 預覽（選做） | E 3D | P4 + P6 | Lab 06 |
| 每週營運摘要（訂單、評論） | F 自動化 | P5 + P2 | Lab 07 |
| 監看附近店家的活動與價格（選做） | G 工具操作 | P6 | Lab 08 |
| 店的吉祥物 3D 角色與小遊戲（選做） | 複合 | P1 + P4 + P3 | Lab 09 |
| 開幕活動錄影剪成精華（選做） | 複合 | P2 + P3 | Lab 10 |
| 吉祥物動畫廣告（選做） | 複合 | P4 + P1 | Lab 11 |

這個 Capstone 要練的是本 Repo 最核心的能力：

> **先分應用目的 → 再拆底層模式 → 最後映射工具。**

## 2. 交付物

1. **系統架構圖**：用 AI Application 六元素（Model / Context / Tools / Orchestration / Runtime / Verification）標註每個元件
2. **問題特性分析表**：每個子系統各填一份（[模板](../../taxonomy/problem-characteristics.md)）
3. **至少三個可運作的子系統**，其中必須包含：
   - 一個給客人用的（網站或 AI 店員）
   - 一個生成媒體（短影音或主視覺）
   - 一個會自動重複執行的（Workflow）
4. **子系統之間要有資料流**，例如：
   - AI 店員的訂單 → 寫入 Sheet → 每週 Workflow 讀取並產生摘要
   - 網站的菜單資料 = AI 店員的知識來源（單一資料來源）
5. **5 分鐘展示 + 一頁「如果真的營運，哪裡會先壞」的風險分析**
6. 每個子系統的 [實作紀錄表](../_record-template.md)

## 3. 評分重點

| 項目 | 比重 | 看什麼 |
|---|:---:|---|
| 拆解與選擇理由 | 30% | 為什麼這個子系統用這個 Pattern？有沒有考慮過別的？ |
| 系統整合 | 25% | 資料是否只有一個來源？子系統能否串起來？ |
| 可運作程度 | 20% | 真的能用嗎？現場展示 |
| 驗證設計 | 15% | 每個子系統怎麼確認它做對了？人工驗收花多少時間？ |
| 風險意識 | 10% | 個資、錯誤訂單、生成內容標示、成本失控 |

## 4. 建議的設計原則

1. **單一資料來源**：菜單只存在一個地方（例如 `menu.json` 或 Google Sheet），網站、AI 店員、宣傳文案都從這裡讀
2. **確定的步驟交給確定的機制**：價格計算、日期、去重用程式；只有「理解」與「生成」交給 AI
3. **能用 API 就不要點畫面**：P6 是最後手段
4. **高風險動作留給人**：下單確認、對外發布、付款
5. **量測驗收成本**：每個子系統記錄「人要花多少分鐘確認它可以用」
